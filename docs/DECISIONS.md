# Decisions

Append-only. One entry per decision: what, why, consequence. Never edit an old entry; add a new one that supersedes it.

## 2026-10-22 Backend is Firebase, not Express/Postgres
PRD v1.3 chose Firebase (Auth, Firestore). `KnowledgeBase/QAMPUS_Technical Design Document.md` (v2.0) is superseded in full; keep it for its ideas (ERD, rules R-40, R-46), not its deployment.

## 2026-10-22 Google sign-in via the native library + Firebase JS SDK
`@react-native-google-signin/google-signin` yields an ID token, then `signInWithCredential`. Needs a development build (not Expo Go). Staff sign-in will use the same provider.

## 2026-10-22 EAS development build; JS changes ship over the air
Rebuild only for native changes (new native package, `app.json` plugins, `google-services.json`). JS-only changes use `eas update`. `expo-updates` uses `runtimeVersion: appVersion`.

## 2026-10-23 Firebase Spark plan only, no Cloud Functions
Cost. The backend is Firestore Security Rules plus a shared client service layer. Consequences: no server-side transactions or queries beyond the client SDK; at most 20 document lookups per rule evaluation; no push sender (open question); daily quotas 50k reads / 20k writes.

## 2026-10-23 Trust model
Student and guest clients are treated as hostile; rules enforce state transitions, ownership and the 60 s grace window using `request.time`. Assigned staff are trusted but fenced to their office.

## 2026-10-24 Backend code is modular by feature, inside the repo
Features: `identity`, `offices`, `ticketing`; later `penalties`, `notifications`, `display`. Each has `service` / `data` / `preflight` (pure checks). Service functions take `db` as the first argument so mobile and staff each inject their own. Planned home: `packages/backend` (not created yet). Apps keep their hooks as thin adapters.

## 2026-10-24 Ticketing slice 1 scope
Join, call next, verify arrival, complete, cancel (WAITING only), no-show. Deferred: offenses and bans, three-ticket limit, capacity cutoff, override, ID verification, guests, notifications and push, display, queue close, activity log.

## 2026-10-24 Slice 1 data model
`users/{uid}`, `offices/{id}`, `staff/{email}`, `queues/{officeId}_{yyyymmdd}` (`last_seq`, `last_called_seq`, `current_ticket_id`), `tickets/{queueId}_{seq}`. Ticket IDs are create-only so a sequence number cannot repeat. Office codes live in a locked `officeCodes/{id}` doc that only rules can read. All timestamps must equal `request.time`.

## 2026-10-24 Staff sign-in: Google popup on web + `staff/{email}` doc
The doc (seeded by hand in the console) holds `office_id`; missing doc means the Not Assigned screen.

## 2026-10-24 Test on the real Firebase project; no emulator for now
A few test accounts stay far below the Spark quotas. Add the emulator later, only for automated rules tests, once several rules exist.

## 2026-10-24 Replace mock data per feature, not all at once
Each hook is swapped for the real one as its feature lands; `mock.js` is deleted last.

## 2026-10-24 Project docs live in `docs/` and are updated every session
`STATUS.md` is overwritten; `DECISIONS.md` is append-only. `AGENTS.md` tells every session to read and update them.

## 2026-10-24 Final slice-1 data model (supersedes "Slice 1 data model" above)
Reconciled against the mock shapes and what the view mappers read. Field names follow the mock/TDD (`daily_sequence`, `short_name`, snake_case). Times are Firestore timestamps and must equal `request.time` on write.

```text
users/{uid}                     role STUDENT|GUEST, name, email, institutional_id, program, guest_type,
                                push_enabled, push_token, strike_count, banned_until, active_count, created_at
offices/{officeId}              code, name, short_name, location, counter_label ("Window 2"), status ACTIVE|INACTIVE,
                                default_service_minutes, utc_offset_minutes,
                                hours { MON..SUN: { open_min, close_min } }  (minutes since local midnight; missing day = closed)
officeCodes/{officeId}          qr_code (= office code, what the QR encodes), manual_code (6 digits). Locked: only rules read it
staff/{email-lowercase}         office_id, role STAFF|SUPER_ADMIN, name ("N. Reyes"), full_name
queues/{officeId}_{yyyymmdd}    office_id, queue_date (int yyyymmdd), status, last_seq, last_called_seq,
                                current_ticket_id, current_ticket_number (short, for "Now serving"), created_at, updated_at
tickets/{queueId}_{seq}         queue_id, office_id, office_code, office_name, queue_date, user_id,
                                holder_name, holder_institutional_id, holder_role,        (snapshot so staff never read users/)
                                daily_sequence, ticket_number (CODE-MM-DD-SEQ), short_ticket_number (CODE-SEQ),
                                status, cancelled_by USER|OFFICE|SYSTEM,
                                joined_at, called_at, service_started_at, completed_at, cancelled_at, no_show_at
```

- **Not stored, derived on the client:** position, `ahead_count`, estimated wait, waiting count. Waiting is approximated as `last_seq - last_called_seq` (cancel gaps overcount slightly); an exact counter comes later if needed. Estimated wait = waiting x `default_service_minutes` until a measured average exists.
- **Manual code** is the static 6-digit check-in code printed beside the office QR. It is the fallback when the camera fails (R-21) and is checked the same way as a scan: verification accepts either the QR payload (`qr_code`) or `manual_code`. Static by design (PRD R-20); it proves possession of the code, not presence (known limitation 9). Kept in `officeCodes` so the app cannot read it from Firestore.
- **Hours** are a per-day map in minutes (not the mock's single `operating_hours` object) so rules can compare against local time computed from `utc_offset_minutes`. UI formats them for display.
- **Queue open/close:** in slice 1 the queue doc is created `OPEN` by the first join of the day, and only when now is inside today's hours. Manual open/close is a later slice.
- **Staff office list:** each office's "now serving / waiting / wait" comes from its own queue doc, so the offices screen listens to one queue doc per office. No queue doc today means "open if inside hours, nobody waiting".
- **Programs list** stays hardcoded in app constants for now.
- **Reserved shapes, not written in slice 1:**
  - `users/{uid}/notifications/{id}`: type, title, message, ticket_id, office_id, is_read, created_at, read_at
  - `offenses/{id}`: user_id, ticket_id, office_name, ticket_number, type, resulted_in_ban, revoked_by_user_id, revoked_at, created_at
  - `events/{id}`: entity_type, entity_id, action, from_status, to_status, actor_uid, actor_name, reason, ticket_number, office_id, created_at
- **Known gaps accepted for slice 1:** no limit on active tickets per user or office; tickets from earlier days that were never closed still exist, so Home shows only active tickets whose `queue_date` is today; the existing client-side `users` create must be locked down by rules (role `STUDENT`, `strike_count` 0, `banned_until` null, `active_count` 0).
- **UI mapper changes this implies:** `toOfficeView` reads today's entry of `hours` and the office's queue doc instead of `office.queue`; `toTicketView` takes the counter label from the office and computes position/ahead/wait from the queue doc.

## 2026-10-24 Check-in code lives on the office doc; no `officeCodes` collection
One 6-digit `check_in_code` on `offices/{id}` serves both the QR and manual entry. The QR is posted publicly and a photo can be shared, so hiding the code from the app only stops the laziest remote check-in; staff no-show (including `IN_SERVICE → NO_SHOW`, R-23a) covers abuse. Saves a collection, a seed doc and a rules lookup. Supersedes the `officeCodes` parts of the earlier data-model entries. A rolling QR (rejected in PRD R-20) would need its own doc for the rotating secret.

## 2026-10-24 Schema locked: users, institutionalIds, offices, staff, queues, tickets
Field sets in `docs/SCHEMA.md` are fixed per collection. Locking is about the shape only; seeding and implementation stay per slice (ticketing slice 1 uses `users`, `offices`, `staff`, `queues`, `tickets`; `institutionalIds` comes with profiles and guests). A locked collection changes only through a new entry here.
- `offices` keeps `short_name` (the UI uses it heavily) and `check_in_code`; no `counter_label`, no timezone field (campus constant UTC+8).
- `tickets` keeps both `user_id` (the uid, used by rules and student queries) and the `holder_*` snapshot (staff cannot read other users' profiles, and rules cannot query for the ticket's owner). One timestamp per status. No push token and no offense fields.
- Still draft: `offenses` (decide fold-into-tickets vs separate before slice 2), `events`, `notifications`, `announcements`.

## 2026-10-24 Offenses stay a separate collection (locked)
Not folded into `tickets`. An offense is a record with its own lifecycle (revoke, Bans & Warnings list, staff offenses screen), matches the PRD's "OFFENSE is the penalty record" (R-26), and keeps offense fields out of the ticket doc the student owns, so the ticket rules stay simple. Implemented in slice 2. `tickets` stays as locked, with no offense fields.

## 2026-10-24 Staff access is the `staff/{email}` doc, not the email domain
Staff sign-in does not check the school domain. A person is staff only if `staff/{lowercase email}` exists; its `office_id` and `role` come from the doc, and a missing doc means Not Assigned. This lets a personal Gmail be seeded as staff for testing while the student app keeps its `@tip.edu.ph` check. `name` in the doc is optional: the app shows `staff.name`, else the Google `displayName`. Only seed emails you trust, since the doc is the whole gate. Rules already let a user read only the doc whose ID is their own email and let nobody write it.

## 2026-10-24 Empty Firebase Auth users from unmatched staff logins are accepted
Rules govern Firestore, not Auth, so a Google account with no `staff` doc still creates an Auth user; it has no data access. Blocking creation needs Identity Platform and Cloud Functions (not on Spark). A client-side `deleteUser` after the popup is possible but bypassable and was declined for now. Revisit if the Auth user list becomes noisy.

## 2026-10-24 Firestore rules are deployed from the repo
`firestore.rules` is the only source of truth; `firebase deploy --only firestore:rules --project qampus-d0718` replaces the whole active ruleset, so the file must always hold every rule. Never edit rules in the console (the next deploy would wipe the edit). `active_count` joins `role`, `strike_count` and `banned_until` as fixed at create (must be 0) and never client-writable; mobile now writes `active_count: 0` on the first profile. `.firebaserc` pins the default project so a deploy cannot hit another one.

## 2026-10-24 `packages/backend` is the one shared Firestore layer
A workspace package (`@qampus/backend`) at the repo root, used by both apps through `"@qampus/backend": "*"`; there is a single copy. Layout: `src/ticketing/{ids,derive,preflight}.js` (pure, no Firebase, unit tested with `npm test` in the package) and `{data,service}.js` (Firestore). Every function takes the app's own `db` first, since mobile and staff initialize Firebase for different platforms. `firebase` is a peer dependency, hoisted once at the repo root. Backend files import `@qampus/core` subpaths (`/domain`, `/format`) so the pure files also run under plain Node. `identity` (profiles, staff lookup) stays in the apps for now.

## 2026-10-24 Staff open the queue manually; students never create queue docs (supersedes "first join creates the queue")
No doc for today means the queue is closed. Staff of the office create `queues/{officeId}_{yyyymmdd}` (status OPEN, counters 0) by pressing Open queue, and can close and reopen it the same day; each new campus day starts closed. Office `hours` are display only, not a join gate. Students join only an OPEN queue: the ticket create must take exactly `last_seq + 1` and the queue bump must come in the same write (rules use `getAfter`/`existsAfter`). Field sets are unchanged, so the locked schema stands. Reason: a scheduled open does nothing when no one is at the counter. Consequence: rules need no hours or timezone math for students; the campus day (UTC+8) is computed from `request.time` only to match document ids.

## 2026-10-24 Derived ticket values are not stored (slice 1 mapping)
Short number (`CODE-SEQ`), position, people ahead, now serving and estimated wait are derived on the client from the ticket and queue docs (`derive.js`, `toShortTicketNumber`). Waiting is `last_seq - last_called_seq`; estimated wait is people ahead times `default_service_minutes`. Mobile mock hooks `useOffices` and `useMyTickets` no longer read `mock.js`.

## 2026-10-24 Calling a ticket (slice C)
Staff call a WAITING ticket of their office only while the queue is OPEN and the window is free (`current_ticket_id` is null). One atomic write: the ticket becomes CALLED (`called_at` = `request.time`) and the queue gets `current_ticket_id` and `last_called_seq = max(old, ticket number)`, checked in rules with `getAfter`/`get`. Call next picks the lowest WAITING number; override calls any WAITING ticket (a reason and the activity log come with the events slice). Because `last_called_seq` never moves backwards, an override can leave earlier tickets overcounted in "people ahead", an accepted slice-1 imprecision (waiting is already approximate). Staff read the office's tickets for today with one query (office_id + queue_date), and a ticket shows its holder's name and ID only: the locked schema has no program on a ticket.

## 2026-10-24 Verify arrival (slice D)
A CALLED ticket becomes IN_SERVICE (`service_started_at` = `request.time`) only while `request.time <= called_at + 60 s`, by the ticket's holder (check-in with the office code) or by staff of the office (verify by the holder's ID). Rules fix who, when and which fields change; the code and the ID are compared in the apps (`checkCheckIn`, `checkVerifyById`), because the locked schema has no field to carry them and the office `check_in_code` is readable by design (R-20, see the check-in code decision). The student check-in is manual entry of the 6 digits for now; QR scanning needs `expo-camera`, a native module, and so a new dev build, and is deferred until the developer decides. Staff Verify, Complete and No-show for an expired ticket: only Verify is real after this slice.

## 2026-10-24 Finishing a ticket (slice E)
The window is freed by the same write that finishes the ticket (the queue's `current_ticket_id` becomes null, checked with `getAfter`). Staff complete an IN_SERVICE ticket (the queue also gets `completed_count` +1 and `service_seconds_total` += the visit's length; staff are trusted, so rules only check that the count rises by one and the total does not fall). Staff mark a no-show on a CALLED ticket only after `called_at + 60 s` (server time), or on an IN_SERVICE ticket with a non-empty reason (`reason`, `no_show_at`). A student cancels only their own WAITING ticket (`cancelled_by` USER, `cancelled_at`); the cancel button is hidden once the ticket is called, because cancelling after a call is an offense and offenses belong to the penalties slice. No offense, strike or ban is recorded by a no-show yet. Staff "Cancel entire queue" is not wired to Firestore yet (it still only changes the mock state).

## 2026-10-24 A student may cancel a CALLED ticket (supersedes the cancel rule in "Finishing a ticket")
PRD R-11 allows cancelling a called ticket, expired or not, after a confirmation that names the offense. The earlier slice E decision hid the button once called; that was a scope choice, not the PRD. Now a student cancels a WAITING ticket (free, one write) or a CALLED ticket; the latter is the ticket at the window, so the same write sets the queue's `current_ticket_id` to null (rules: `validCancel` plus a queue clause for the ticket's owner). A ticket in service cannot be cancelled. The offense, strike and ban for a called cancellation, a no-show and an expired-unmarked cancellation are all recorded by the penalties slice; until then nothing is recorded, although the confirmation already tells the student it counts.

## 2026-10-24 Office cancels the queue; the ticket-flow mocks are gone (slice F)
"Cancel entire queue" (R-16) is real: one transaction reads every ticket number the queue issued today (1..`last_seq`), cancels each unfinished one as `cancelled_by` OFFICE with the reason (stored in `reason`), clears `current_ticket_id` and closes the queue. Rules tie each ticket write to the queue's closing with `getAfter`, and require a non-empty reason. Nobody is penalized. The staff `QueueProvider` keeps no mock queue state any more: the dead mock reducer paths (call, verify, no-show, complete, open, close, cancel), their validators and `MOCK_STAFF_QUEUE`, `MOCK_ACTIVE_TICKETS`, `MOCK_HISTORY_TICKETS` and the unused mock users were deleted. Consequence: the staff Activity Log (still mock) no longer gains entries when staff act, because the mock reducer was the only thing writing them; real entries arrive with the events slice. `MOCK_OFFICES` stays for the public display (staff `useOfficeByCode`), which needs its own rules (no session) and slice.

## 2026-10-24 Three-ticket limit (R-07): a counter on the student, kept simple
A student holds at most three active tickets (WAITING, CALLED, IN_SERVICE) across all offices. The counter is `users.active_count` (already in the locked schema; no new field). A join must raise it by exactly one in the same write as the ticket and only while it is below three (ticket rule), so the check cannot be skipped. Complete, no-show, student cancel and office cancel lower it by one in the same transaction. Rules let a student move their own counter by one within 0..3 and let staff lower it by one. Rules cannot see why the counter moved, so a hand-made client (any signed-in school account can call Firestore without the app) could lower its own counter and hold more than three; accepted for the prototype. A stricter version (every decrement tied to a ticket that finishes in the same write, via a `released_ticket` field) was built and dropped as too much code for this stage.
Consequences: an unfinished ticket from an earlier day holds a slot until cancelled, so Home shows every active ticket, not only today's. Office cancel runs in small transactions (queue close and the ticket at the window first, then waiting tickets in groups of at most 3, never two of one holder together; run it again to finish an interrupted run). Tickets that were active before the counter existed were never counted; reset them (delete the test tickets and queue doc, set `active_count` to 0) or finishing them is refused. Next: no double join of the same queue.

## 2026-10-24 One active ticket per office: `users.active_offices`
A student cannot join an office where they already hold an active ticket (WAITING, CALLED, IN_SERVICE), so the same queue cannot be joined twice, from one phone or two. Rules cannot query tickets, so the fact lives at a known path: a map on the student's users doc, `active_offices` (office id -> true), added to the locked schema as a new field. A join checks it and sets it in the same write as the ticket and the counter (the ticket rule requires both); every write that lowers `active_count` (complete, no-show, student cancel, office cancel) clears that office with `deleteField()`. Two joins at once collide on the same users doc, one retries and sees the entry. Same trust level as the counter: a hand-made client could clear its own map; accepted for the prototype. An unfinished ticket from an earlier day keeps the office blocked until it is cancelled (it is on Home). New profiles are created with `active_offices: {}`; existing docs get the field on their first join.

## 2026-10-24 Penalties: offenses, strikes and bans (R-11 to R-16)
An offense is a document `offenses/{ticketId}` (same id as its ticket, so a ticket causes at most one). It is created in the same transaction as the ticket change that causes it: the holder cancelling a CALLED ticket (`CANCELLED_AFTER_CALL`, expired or not), or staff marking a CALLED or IN_SERVICE ticket a no-show (`NO_SHOW`). The same transaction moves the holder's counters on `users`: the first offense sets `strike_count` to 1; the second resets it to 0, sets `banned_until` to 24 hours ahead and marks the offense `resulted_in_ban`. Office and system cancellations record nothing (R-16).
Rules: a CALLED cancel and a no-show are refused unless the offense is created in the same write (`existsAfter`), so a student cannot skip their own penalty; the offense must copy its ticket, say correctly whether it causes a ban, and the holder's `strike_count` must move exactly as R-13 says (`getAfter`). A student or staff may move strikes only toward a penalty; only staff of the offense's office lower them, by revoking. A join is refused while `banned_until` is in the future (R-14, server time). The 24-hour end is written by the app (rules cannot add 24 h to the server time in a write), so rules accept it within half an hour of request.time + 24 h.
Schema: `offenses` gains `holder_name`, `holder_institutional_id` (snapshots, as on tickets, so staff need no user read) and `revoke_reason`. Staff may read a single student profile (`get` only, no list), because recording an offense needs the current strike count; the profile holds an email and a program, which staff of the school already see.
Revoke (R-15): staff of the offense's office revoke it with a reason; the record stays (`revoked_at`, `revoked_by`, `revoke_reason`). Prototype semantics: revoking the offense that caused the ban lifts the ban and sets the strikes back to 1; revoking any other offense lowers the strikes by 1 if there is one. There is no super administrator: the database owner acts through the console. The staff Offenses summary is derived from the offenses that office can see (display only), so a student with offenses at another office can differ from the profile, which is what counts.
Deferred: notifying the student of a no-show or a revoke (notifications slice) and activity-log entries (events slice).

## 2026-10-25 Activity log: a stored `events` collection, 50 per page (locked)
The staff Activity Log (R-28) reads `events/{autoId}`: entity_type TICKET or QUEUE, entity_id, action, from_status, to_status, actor_uid, actor_name, reason, office_id, ticket_number (full), created_at. One line is written inside the transaction or batch of each action (`logEvent`, `@qampus/backend/events`), so it commits with the change: open, close and cancel queue, join, call, override, verify, complete, no-show, student cancel. It was chosen over deriving the log from tickets (the way mobile History is a view of ticket docs) because tickets keep no staff actor and no queue-level actions. Each staff action takes `actor` `{ uid, name }`; student actions use the holder.
Rules: create-only; fixed fields; `actor_uid == request.auth.uid`; `created_at == request.time`; no lookups; read by staff of the office. Accepted weaknesses (same trust level as the counters): any signed-in client may write a false line into an office's log, and nothing requires a line alongside a change. Office cancel writes one QUEUE_CANCELLED line with the reason (no ticket count). The override line has no reason yet because the override modal does not ask for one.
Reading: `where office_id`, optional `action` and `created_at` bounds, `orderBy created_at desc`, `limit 50`. Page 1 is a live listener; Older loads the next page once with `startAfter`; Newer steps back (no total, no page jumps). Needs two composite indexes (`firestore.indexes.json`). Not logged: invalid scan, offense lines (the Offenses screen shows them), cutoff override (comes with the cutoff slice).

## 2026-10-25 In-app notifications: a mailbox written with the change that causes them (locked)
`users/{uid}/notifications/{autoId}`: type, title, message, ticket_id, office_id, is_read, created_at, read_at. Each is one more write inside the transaction of the change: YOUR_TURN to the called student, APPROACHING_TURN to the student `RULES.APPROACHING_PLACE` (3) places back (chosen on the staff client from the live waiting list, no extra read, so it can name a ticket that has just left the line), NO_SHOW with the strike or ban consequence, QUEUE_CANCELLED to every cancelled ticket (one per ticket, inside the existing groups of 3), OFFENSE_REVOKED with the reason, QUEUE_CONFIRMED to the student on join. Cancelling a called ticket is an offense the student causes themselves, so the student writes their own WARNING (same consequence text); there is no separate ban notice type: the message says when the offense causes the 24-hour ban. Text lives in the pure `buildNotification`.
Rules: shape checks only, no lookups; created unread with server time; staff may create for any student, the owner only QUEUE_CONFIRMED and WARNING; only the owner reads; the owner may only mark one read (`is_read`, `read_at`); no delete. A hand-made client could write a false notification into its own mailbox; accepted. Read: the latest 50, newest first, one listener in `QueueDataProvider` (no composite index). SERVICE_COMPLETED, GLOBAL_ANNOUNCEMENT and staff notifications are not written yet; push is a separate follow-up (needs `expo-notifications`, a new dev build and a sender decision).

## 2026-10-25 Capacity cutoff and measured wait times (R-17 to R-19), client side only
`cutoffState({ office, queue, now })` (ticketing/derive.js, unit tested, campus time UTC+8) refuses a join when `minutes until close / average visit < waiting + 1`, or once the office's closing time has passed; staff can override it for the day (`queues.cutoff_overridden`, one write plus a `CUTOFF_OVERRIDE` event, reset by the next day's queue doc). Enforced in the client only (the join check in `joinQueue`, which reads the stored office for its hours, and the Join button reason): a hand-made client could join past the cutoff, accepted for the prototype (R-30 prefers server enforcement). Rules gain one clause so staff can set `cutoff_overridden` to true (that field and `updated_at` only).
Simplifications: the average visit is today's `service_seconds_total / completed_count` (the PRD says today and yesterday), else the office default; an office with no hours for the day has no cutoff, so a queue opened on a closed day still accepts joins; a queue opened before the opening time is not refused. The cutoff moves as the line changes (`cutoffAt` is the latest instant a join is accepted with today's waiting count). The staff cutoff banner and header strip read it; the "cutoff approaching" warning is derived there, so no staff notification doc is stored. The wait estimate everywhere is people ahead times the average, rounded.

## 2026-10-25 Notifications are read by viewing; a banner announces new ones in the app
Opening the Notifications screen marks every unread notification read (one `markRead` per id, also for ones that arrive while it is open), so the bell clears without tapping; the ones that were new stay highlighted until the student leaves the screen. While the app is open, a new unread notification slides in as a subtle banner from the top for 5 seconds (tap opens the list). It is not shown for QUEUE_CONFIRMED and WARNING (the student just caused them), nor YOUR_TURN (the "It's your turn" dialog announces it), nor on the Notifications screen, and only for notifications created in the last 2 minutes so opening the app does not replay the mailbox. This is in-app only; a notification while the app is closed still needs push (separate follow-up).

## 2026-10-25 Small issues: locked student ID, refusal banner, root cleanup
Edit Profile saves a student's program only; the student ID stays as first saved (PRD R-01; the rules already refuse a change once `institutional_id` is set, and 6.6 will claim IDs for uniqueness), so DoD #22's "editable" is not followed. A guest's edits stay in memory until guests have a profile document (6.6). A refused staff action now shows a banner (`Couldn't <what>. <reason>`, reasons keyed by `TicketingError`) on every console screen instead of only logging. The stray root `app.json` (EAS project and owner differing from `apps/mobile/app.json`) was deleted and the root README rewritten; the root `eas.json` is left for a later decision.

## 2026-10-25 Guests and unique IDs: anonymous accounts, institutionalIds claims (slice 6.6)
"Continue as guest" is `signInAnonymously` (the account lives on the device, R-02). The guest profile and the unique Guest ID (`G` + six digits) are saved in one transaction (`issueGuestProfile`): it picks a random candidate, reserves `institutionalIds/{id}` (`{ uid }`, create-only) and writes the profile; a taken ID is retried up to 8 times. The ID is generated in the app because Spark has no server; uniqueness is enforced by the rules, which departs from R-30's "server issues it". Student IDs are reserved the same way (`claimStudentProfile`, 7 digits); a second account entering a registered ID is refused (`ID_TAKEN`), and a wrong claim is fixed by the developer in the console.
Rules: a claim is created only by its owner, with the id shaped `G[0-9]{6}` for an anonymous account or `[0-9]{7}` for a school account, and only together with that same ID on the owner's profile (`getAfter`); a change of `users.institutional_id` requires its claim in the same write. Any signed-in user may `get` a claim (the app must see an ID is taken); it exposes only the owner's uid. Students who saved an ID before this slice have no claim (no backfill; accepted). Guests are otherwise treated like students (limits, penalties, notifications). A guest may sign out after a warning, which deletes the guest identity for good (no way back into an anonymous account). Clearing app data or reinstalling makes a new guest and a new ID (PRD known limitation 1). ## 2026-10-25 Push notifications: a relay on Cloudflare Workers, not Cloud Functions
Sending a push must come from a trusted server: the staff web page cannot call Expo's push API (its CORS preflight returns no `Access-Control-Allow-Origin`, verified), the phone cannot wake itself when the app is closed, and Firebase Cloud Functions need the Blaze plan (a billing card), which the 2026-10-23 decision to stay on Spark avoids. So a small relay runs on Cloudflare Workers' free plan (100,000 requests a day): the staff console posts `{ to, officeName }` with its Firebase ID token; the relay proves the caller is staff by reading `staff/{email}` over Firestore's web API with that same token (the rules let a user read only their own staff doc, so no admin key is stored), then sends a fixed "your turn" message to Expo (`channelId`, `priority: high`, `ttl: 120`). Only "your turn" is pushed (R-25). Receipts are not processed (no scheduled job on this setup); a dead token fails silently. Android only for now. If the project later moves to Blaze, a Firestore-triggered Cloud Function would replace the relay (simpler and independent of the staff page staying open).

## 2026-10-25 Push notifications: how the relay design was built
Student app (`apps/mobile/src/lib/push.js`, `usePushRegistration`): after sign-in with a live profile whose `push_enabled` is not false, the phone creates the Android channel `default` first, asks permission once, gets the Expo push token (`getExpoPushTokenAsync({ projectId })`, only on a real device) and saves `users.push_token` on every app start. The Settings switch saves `push_enabled` to Firestore (off also clears the token). Sign-out clears the token before the session ends, for students and guests. The foreground handler shows nothing (the in-app banner and the called dialog already do); a tap opens Home. Staff console (`apps/staff/src/lib/push.js`): after a call succeeds, `callTicket` resolves to `{ id, user_id, ticket_number }`, the console reads that student's profile (staff may `get` one), skips when there is no token or push is off, and POSTs `{ to, officeName }` with its Firebase ID token to `EXPO_PUBLIC_PUSH_RELAY_URL/push`; it is best effort and never throws. Relay (`relay/`, a Cloudflare Worker): proves the caller is staff by reading `staff/{email}` over Firestore's web API with the caller's own token (a forged or non-staff token is refused by the rules), checks the browser origin against `ALLOWED_ORIGINS`, and sends only the fixed message ("It's your turn" / "Go to {office} and check in within 1 minute.", `channelId` default, high priority, ttl 120 s, `data.type` YOUR_TURN). Also fixed: `callTicket` shadowed the override `reason` with the refusal check, so an override reason would never have reached the log.
